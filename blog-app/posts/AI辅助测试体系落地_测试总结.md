## 一、我为什么搭这套体系（背景 & 测试职责）

我接手的是公司核心信贷营销相关系统的质量保障，业务线多、迭代快：信贷营销核心系统联动 6 个核心服务，覆盖权益 / 支付 / 下单链路；还有 521 品牌日大促（358 万用户池）、金币借款任务二期等周期性重点项目。

最大的痛点是「用例维护跟不上迭代」：活动规则、权益玩法频繁变，UI 元素一改，原有一堆定位脚本就废了，回归成本极高；接口用例也散在各个同学本地，没统一框架、没持续集成。我作为自动化测试负责人，核心职责就是：

- 用 AI 把「用例设计 + 脚本编写」前移，降低维护成本
- 搭一套可复用、可回归的接口自动化框架
- 把多条业务线的质量保障拉到统一标准，扛住大促峰值

一句话定位：我不只是写用例的人，而是给多业务线搭「AI 辅助 + 自动化」质量底座的人。

## 二、AI 辅助测试工作流怎么搭的（Codex CLI + Playwright MCP）

思路：提测后不等人手写，而是用预置的 Prompt / Skill 模板驱动 AI 读需求文档和代码分支，自动产出测试用例和 Playwright 断言脚本。核心是把「人读文档 → 人写脚本」变成「模板驱动 AI → 人抽检补全」。

我定义了三类模板（伪代码思路）：

```python
# 1) 用例生成模板：喂需求文档，产出结构化用例
CASE_GEN_PROMPT = """
你是资深测试工程师。请基于【需求文档】与【接口定义】设计测试用例。
按 等价类 / 边界值 / 异常场景 分类，每条用例含：
前置条件、步骤、预期结果、所属链路。只输出 JSON 列表。
需求文档：{prd}
接口定义：{api_spec}
"""

# 2) 脚本生成 Skill：用例 → Playwright 断言脚本
SCRIPT_GEN_SKILL = """
读取上一步用例，结合 MCP 提供的页面 DOM / 路由信息，
生成 Playwright 断言脚本（优先用语义定位，避免脆弱的 XPath）。
输出可直接运行的 .spec.ts 文件。
"""

# 3) 回归校验：AI 生成 → 人工抽检 → 场景补全
def ai_test_workflow(prd, api_spec, branch):
    cases   = codex.generate(CASE_GEN_PROMPT, prd, api_spec)   # 产出用例
    scripts = codex.apply_skill(SCRIPT_GEN_SKILL, cases, branch)  # 产出脚本
    sampled = human_review(scripts, ratio=0.3)                 # 人工抽检 30%
    patched =补全边界场景(sampled)                             # 场景补全
    return patched
```

落地效果：UI 用例维护效率提升约 **60%**——原来活动改版要重写上百条定位，现在模板驱动重新生成 + 抽检即可；AI 测试方案可用率约 **85%**（即 85% 基础功能用例可由 AI 方案覆盖，剩余靠人补）。

踩坑提醒：AI 生成的脚本不能「生成即信任」。我坚持「生成 → 人工抽检 30% → 边界补全」三步走，否则大模型会编出看似合理但跑不通的断言。

## 三、接口自动化框架（分层设计）

AI 解决「写得快」，但接口自动化的「稳和可复用」还得靠正统框架。我用 **Python + Pytest + Requests** 搭了分层框架，把数据、逻辑、场景拆开：

```python
# 数据层：用例数据外置，yaml / json 驱动
test_cases/
  ├─ data/            # 入参、期望结果（参数化）
  ├─ logic/           # 封装请求、断言、鉴权
  └─ scenario/        # 业务场景编排（下单链路、支付链路）

# 逻辑层示例：统一请求封装
def call_api(name, **kwargs):
    conf = load_case(name)                 # 读数据层
    resp = requests.request(conf.method, conf.url, **kwargs)
    assert resp.status_code == conf.expect_code
    return resp

# 场景层示例：链路编排
def test_order_flow():
    login(); create_order(); pay(); assert order_done()
```

- 沉淀 **400+** 可复用用例，覆盖核心链路
- 接入 **Jenkins**：代码提交即跑 + 每日定时巡检，失败自动告警
- 累计全业务线交付 **500+** 自动化用例，核心链路自动化率 **80%+**

设计原则：数据层与逻辑层分离，业务同学改数据不改代码，降低协作门槛；场景层用关键字编排，新链路能快速拼出来。

## 四、多业务线质量保障怎么落地的

框架是底座，真正扛压是在具体业务线。三条线我分别抓了重点：

**1) 信贷营销核心系统（常态化保障）**
- 联动 6 个核心服务，覆盖权益 / 支付 / 下单链路
- 用分层框架做日常回归 + 接口巡检，全年零重大故障、零资损

**2) 521 品牌日大促（峰值保障）**
- 358 万用户池，7 阶梯抽奖 + 多客群投放 + 实时库存
- 核心接口 **80% 自动化覆盖**，灰度放量前全量回归
- 梳理任务资格 / 抽奖规则 / 库存管理场景，发现并推动修复 **40+ 缺陷（含 12 个 P0 上线前闭环）**

**3) 金币借款任务二期（高频迭代保障）**
- 活动规则变得快，原 UI 自动化维护成本高
- 引入 **Midscene.js** 用自然语言指令写 UI 用例，替代脆弱的元素定位，落地 **120+ UI 用例**
- 对借贷补充机制做**状态机一致性校验**，验证金额发放逻辑，累计修复 **60+ 缺陷（含 10 个 P0）**

关键动作：大促/重点版本走「需求评审 → AI 出用例 → 自动化覆盖 → 灰度校验 → 问题闭环」全流程，缺陷从上线上追到需求侧。

## 五、踩过的坑 & 反思

1. **AI 生成脚本「看似对实际跑不通」**。早期直接信任生成结果，CI 一堆红。后来固定「抽检 30% + 边界补全」才稳住。
2. **Midscene.js 自然语言定位也有歧义**。页面有多个相似按钮时 NL 会点错，关键路径我还是加了显式锚点兜底。
3. **大促数据构造是隐性成本**。358 万用户池的库存 / 资格场景，造数比写用例还费时，后来沉淀了造数脚本复用。
4. **自动化率不是越高越好**。核心链路 80%+ 足够，长尾场景硬写自动化 ROI 低，我把它留给人工探索式测试。

## 七、个人总结

这个项目让我从「手工写脚本的测试」成长为「用 AI 提效 + 用框架兜底」的测试开发。最大的收获不是会用 Codex CLI 或 Midscene.js，而是摸清了一条落地路径：

**AI 负责「写得快」，框架负责「跑得稳」，人负责「定标准和兜底」**——三者分工清楚，自动化才不会变成负担。

也让我确认了一件事：质量保障的价值不在用例数量，而在「迭代越快、质量越稳」。这也是我持续想把 AI 更深融进测试流程的原因。
