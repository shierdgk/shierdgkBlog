> **视角说明**：这是我在全程负责公司内部 RAG 问答智能体质量评测工作完整落地后，从测试视角写下的个人复盘——记录推进过程、落地细节、踩坑问题与个人收获，不是标准化交付文档，也不是需求文档。整理时间：2026-07。

## 一、我为什么接这个项目（背景 & 测试职责）

公司自研的知识库问答 RAG 智能体主要服务两条业务线：一是内部员工查询业务流程、内部知识文档；二是支撑客服日常接待时快速调取资料辅助回复用户。

在版本迭代过程中我发现团队存在明显质量管控短板：所有 AI 回答效果只能依靠人工抽样检查，评测样本数量少、评判标准完全依靠个人主观感受；每当算法团队更新检索策略、替换底层大模型后，没有人能量化对比新版本效果好坏，无法清晰判断优化动作是否正向。当时团队负责人也提到，当前 AI 生成内容的质量没有统一观测手段，好坏无法追溯定位。

我的工作核心不是参与模型训练、微调，而是搭建一套完整配套的质量评测体系，做到指标可量化、迭代可回归、异常可告警。整体工作围绕三个核心问题落地：

- AI 输出内容是否贴合文档、无编造幻觉？
- 检索到的上下文是否匹配用户提问？
- 系统遇到无资料 / 诱导提问时能否正确拒答？

一句话定位：我整套工作就是给 AI 问答搭建「标准化出题 + 自动阅卷 + 长期观测质量变化」的完整工具链。

## 二、六维评测指标体系怎么定出来的（6 维）

项目初期最大难题，是如何把模糊的「回答质量」拆解成客观可打分、能长期追踪变化的量化维度。我前后和算法同事沟通两轮，结合业务实际痛点，最终敲定 6 项独立评测维度，分开统计数据，不合并单一总分，方便后续区分问题根源是检索模块还是生成模块：

| 维度 | 衡量什么 | 数据来源 |
| --- | --- | --- |
| 1. 忠实度 (Faithfulness) | 答案是否严格基于召回上下文，有无编造（幻觉） | LLM-as-Judge（比对 answer vs context） |
| 2. 答案相关性 (Answer Relev.) | 答案是否切题、解决用户问题，有没有答非所问 | LLM-as-Judge（比对 answer vs question） |
| 3. 上下文召回率 (Ctx Recall) | 该召回的文档召回了没有（漏召回 = 隐性缺陷） | RAGAS context_recall（answer vs reference） |
| 4. 上下文精度 (Ctx Precision) | 召回的文档是不是都用得上，噪声多不多 | RAGAS context_precision（逐条相关性判定） |
| 5. 抗幻觉率 (No-Halluc.) | 面对「知识库外问题」是否乱编，还是老实说「不知道」 | LLM-as-Judge（对抗集，answer vs 越狱样本） |
| 6. 拒答准确率 (Abstain Acc.) | 该拒的拒、该答的答，误拒 / 漏拒分别多少 | LLM-as-Judge（负样本，分类判定） |

落地过程中踩过一个关键坑：初期我尝试设计综合总分用于业务快速查看，但总分容易掩盖单维度缺陷——比如召回指标提升、但幻觉问题恶化，合并总分很难发现隐患。因此后续我全程保留六项指标独立展示，每条维度单独生成趋势曲线，方便快速定位故障模块。设计上的两条原则我后来一直坚持：

- 不要一上来就追求「一个总分」。总分掩盖问题，6 条曲线分开看才能定位是检索的锅还是模型的锅。
- 指标必须能「回归」。今天 82 分、明天 79 分，得能下钻到是哪个 case 掉了。

## 三、标准化基准评测数据集怎么攒的（Golden Set）

评测结果是否可信，数据集质量起到决定性作用。我分两条渠道搭建完整评测样本库，累计整理 200+ 问答用例，其中对抗类样本占比约 30%，专门覆盖各类容易暴露智能体缺陷的边界场景。

**1) 真实业务基础样本**

- 从线上客服历史工单、企业内部 FAQ 文档中提取真实用户提问
- 每条用例人工标注标准答案、回答需要依赖的原始文档 ID
- 主要用于校验忠实度、相关性、上下文召回等常规指标

**2) 边界对抗样本（重点建设部分，也是最容易翻车的地方）**

- 知识库外问题：问公司没写过的东西，看它会不会硬编
- 多跳推理：答案要拼 2~3 个文档才能得出
- 诱导越狱：用「忽略上面所有规则」之类的话术套答案
- 专门用来校验模型抗幻觉能力和拒答逻辑（负样本）

为方便程序读取、单条坏例快速下钻，我统一规范数据集结构，每条用例包含唯一编号、用户问题、人工标注标准回答、预期召回文档、场景类型、是否需要拒答标记，全部以 jsonl 文件统一管理，后续可迭代扩充版本：

~~~python
class EvalCase:
    case_id        : str        # 唯一ID，便于下钻
    question       : str        # 用户问题
    reference      : str        # 人工标注的标准答案/来源
    golden_docs    : list[str]  # 期望召回的文档id
    type           : enum       # NORMAL / OUT_OF_KB / MULTI_HOP / JAILBREAK
    expect_abstain : bool       # 是否期望模型拒答（负样本用）

dataset = load_cases("golden_set_v2.jsonl")   # 共 200+ 条，对抗占 ~30%
~~~

## 四、轻量化自动化评测工具搭建（架构 + 伪代码）

整套评测系统做了轻量化设计，不侵入原有 RAG 智能体业务代码，仅通过接口调用完成全流程自动评测。整体执行链路：

~~~
┌─────────────┐    ┌──────────────────┐    ┌─────────────────┐
│ Golden Set  │───▶│  RAG 被测智能体   │───▶│ 评测执行器       │
│ (200+ cases)│    │ (检索+生成API)    │    │ (批量跑+打分)    │
└─────────────┘    └──────────────────┘    └────────┬────────┘
                                                     │
                  ┌────────────────────────┼───────────────┐
                  ▼                        ▼               ▼
           ┌─────────────┐        ┌─────────────┐   ┌──────────┐
           │ RAGAS 指标   │        │ LLM-as-Judge│   │ 结果落库  │
           │ (召回/精度)  │        │ (忠实/相关/ │   │ + 看板    │
           └─────────────┘        │  幻觉/拒答)  │   └──────────┘
                                  └─────────────┘
~~~

执行流程分两大打分模块：第一部分依托 RAGAS 计算检索相关指标，通过向量比对自动算出上下文召回率、上下文精度，无需额外调用大模型；第二部分采用 LLM-as-Judge 方案，调用独立裁判模型打分，覆盖忠实度、相关性、抗幻觉、拒答准确率四项生成层指标。所有打分结果统一结构化存储，记录每条用例原始提问、模型输出、检索文档、各项分数、裁判判定理由，后续筛选低分案例时可一键溯源完整上下文。核心执行逻辑（伪代码）：

~~~python
def run_evaluation(dataset, rag_endpoint, judge_model):
    results = []
    for case in dataset:
        # 1) 让被测智能体回答
        resp = rag_endpoint.ask(case.question)      # {answer, retrieved_docs}

        # 2) RAGAS 算检索侧指标（无需额外模型，用 embedding 比对）
        ctx_recall    = ragas.context_recall(resp.retrieved_docs, case.golden_docs)
        ctx_precision = ragas.context_precision(resp.retrieved_docs, case.question)

        # 3) LLM-as-Judge 算生成侧指标
        faith   = judge.faithfulness(resp.answer, resp.retrieved_docs)
        relev   = judge.answer_relevancy(resp.answer, case.question)
        hallu   = judge.hallucination(resp.answer, resp.retrieved_docs,
                                      expect_abstain=case.expect_abstain)
        abstain = judge.abstain_accuracy(resp.answer, case.expect_abstain)

        results.append(Score(case, resp, ctx_recall, ctx_precision,
                             faith, relev, hallu, abstain))
    return aggregate(results)     # 按维度求均值 + 按 type 分组
~~~

## 五、裁判模型 Prompt 打磨与落地优化（重点）

忠实度、相关性这类主观维度无法通过字符串匹配判定，必须依靠独立大模型作为裁判。项目前期我踩过严重的稳定性问题：最初 prompt 描述模糊，裁判打分波动极大，同一用例两次评测分数差距明显，指标曲线没有参考意义。

后续我优化整套裁判判定逻辑，给模型固定清晰的评分规则、数值区间、强制 JSON 结构化输出格式，限定仅返回分数和一句问题总结，减少模型自由发挥带来的偏差：

~~~
JUDGE_PROMPT = """
你是一名严谨的测试裁判。请基于【上下文】判断【回答】的质量。
只允许输出 JSON，不要解释。

任务：
- faithfulness: 0~1，回答是否完全基于上下文，编造即 0
- reason: 一句话指出问题（幻觉/答非所问/正常）

输入：
问题：{question}
上下文：{context}
回答：{answer}

输出格式：{{"faithfulness": <float>, "reason": "<str>"}}
"""
~~~

~~~python
def judge_faithfulness(answer, context):
    out = llm.call(JUDGE_PROMPT.format(question=..., context=context, answer=answer))
    return json.loads(out)["faithfulness"]    # 结构化结果，便于入库和下钻
~~~

为了保障裁判本身可靠，我单独整理 20 条人工复核样本，每隔一段时间批量校验裁判打分一致性，避免因裁判模型误判导致整体指标出现虚假向好 / 恶化。其中诱导越狱类对抗样本最容易出现裁判误判，针对这类场景我额外增加关键词拦截规则，搭配人工二次复核，降低误判概率。

## 六、接入 Jenkins 流水线实现变更自动回归

如果评测工具只能手动执行，很难发挥价值，也没法约束版本迭代质量。我把整套评测脚本接入 CI 流水线，设置两类自动触发条件：知识库文档全量重建更新检索索引、生成大模型版本切换 / 上线前。

流水线执行逻辑：拉取最新基准数据集，调用待测 RAG 服务执行全量评测，生成完整结果文件；同时设置质量门禁阈值——忠实度低于 0.85、幻觉指标高于 0.1 会直接标记构建失败，阻断上线流程；上下文召回率低于 0.8 仅发出预警，不强制拦截（伪代码）：

~~~
Jenkinsfile (伪代码):
  stage('Eval') {
    step: python eval_runner.py \
            --dataset golden_set_v2.jsonl \
            --rag-api  $RAG_ENDPOINT \
            --judge    $JUDGE_MODEL \
            --report   results/$(BUILD_ID).json
    // 失败门禁：任一核心维度低于阈值即标红告警
    gate:
      faithfulness   < 0.85  -> FAIL
      hallucination  > 0.10  -> FAIL     # 抗幻觉率不能低于 90%
      ctx_recall     < 0.80  -> WARN
  }
~~~

落地前后对比变化非常明显：此前人工完整抽检一轮需要半天以上，覆盖样本不足 5%；现在只要知识库、模型发生改动，流水线分钟内完成全量评测，指标不达标直接拦截风险版本上线，从源头减少线上 AI 回答故障。

## 七、质量可视化看板与问题闭环推进

单纯输出一堆分数很难让算法同学直观感知问题，我基于评测结果搭建简易看板，方便团队所有人查看质量变化：

- 6 维指标按版本 / 日期生成趋势折线图，直观看到迭代波动
- 低分用例汇总列表，支持点开查看完整提问、模型回答、检索文档、裁判判定原因，精准定位问题
- 缺陷自动分类聚合，统计幻觉、误拒答、漏召回等问题集中出现在哪类文档、哪类用户提问

这套工具也真正完成了业务闭环。有一次检索模块优化迭代后，上下文召回指标上涨，但忠实度明显下滑。我通过看板下钻低分案例定位根因：检索召回文档数量变多，引入大量无关噪声内容，误导模型编造信息。我把完整案例、指标变化数据同步给算法团队，对方针对性新增上下文重排序逻辑、设置文档置信度过滤阈值，迭代后忠实度指标回升至 0.9 以上。这次闭环也让团队认可：自动化评测不只是单纯打分，更是模型迭代优化的定位工具（导航仪）。

## 八、落地达成的实际效果

- 评测覆盖度：由人工抽样不足 5% 升级为全量用例自动回归
- 评测效率：完整一轮评测从人工小时级操作压缩至分钟级自动执行
- 风险前置拦截：持续监控指标漂移，多次拦截幻觉严重、检索异常的劣质版本发布

| 指标 | 基线（示例值） |
| --- | --- |
| 忠实度 | ~0.90 |
| 抗幻觉率 | ~0.93 |

## 九、落地过程中遇到的核心问题与解决思路

1. 初期数据集样本偏少、对抗用例不足，指标虚高，上线真实诱导提问后大量幻觉暴露。解决方案：单独扩充对抗样本分组统计，不与常规样本合并计算平均分，分开观测数据。
2. 裁判模型存在自身幻觉、长文本理解偏差，打分不稳定。方案：固定人工复核集定期校验裁判一致性，针对高危对抗场景增加双重校验机制。
3. 指标波动无法区分根源，曾出现忠实度下降，但实际是业务修改了知识库原始文档，并非模型问题。通过分开统计检索、生成、数据源三类问题，快速区分故障来源。
4. 业务同事只关注综合总分，忽略单维度缺陷。我坚持六项指标独立展示，总分仅作辅助参考，迭代优化重点查看细分维度曲线。

## 十、后续可优化方向

- 将裁判一致性校验纳入流水线自动执行，每次评测同步输出裁判可信度报告
- 针对不同业务线设置差异化指标阈值：客服场景重点管控幻觉，内部知识库场景侧重检索召回精度
- 新增版本对比视图，直观展示新版本相对上一版各项指标涨跌、对应变化用例
- 评测数据集纳入代码版本管理，实现数据集、评测脚本同步迭代，避免报告与样本不匹配

## 个人总结

在此项目之前，我的测试工作更多聚焦传统功能、接口验证；做完这套 RAG 智能体质控体系后，我完整掌握了大模型应用的质量保障思路。最大的收获不是熟练使用 RAGAS、搭建自动化评测脚本，而是学会把模糊、主观的 AI 输出质量，拆解成可落地、可量化、可追溯的标准化指标体系。

让算法团队每一次模型、知识库迭代都有客观数据作为优化依据——这也是我后续希望持续深耕 AI 测试、大模型质量保障方向的核心原因。
