## 前言：踩坑后才明白，新项目一定要早做自动化

之前参与过好几个项目，都犯了同一个错误：前期业务简单，全靠人工回归。等到需求迭代变快、模块越来越多，每次发版前完整回归一遍就要大半天，改一行代码都担心牵连其他功能，线上隐性 Bug 层出不穷。

后来我养成习惯：任何新项目启动阶段就搭好自动化测试体系。新项目代码干净、逻辑简单，接入成本极低；越早落地，后期省的时间越多。

我的核心观点：自动化不是为了替代手工测试，而是干掉重复、机械的回归工作，把人力留给复杂交互、用户体验这类需要主观判断的场景。

## 一、我在新项目固定使用的四层测试分层

试过全量 E2E、只写单测两种极端后，我整理出一套性价比最高的分层策略，由底层到上层逐步覆盖，不用一次性写几百条用例。

### 1. 单元测试：底层工具、逻辑兜底（必做）

适用场景：通用工具函数、业务计算逻辑、自定义 Hooks、状态处理方法。前端项目我统一用 Vitest，Vite 项目运行速度远快于 Jest。

~~~bash
npm i -D vitest jsdom @testing-library/vue
~~~

时间格式化函数的例子：

~~~ts
export function formatTime(ts: number) {
  const d = new Date(ts);
  return `${d.getFullYear()}-${d.getMonth() + 1}-${d.getDate()}`;
}
~~~

~~~ts
import { formatTime } from '@/utils/time';
test('标准时间戳输出年月日', () => {
  expect(formatTime(1704067200000)).toBe('2024-1-1');
});
~~~

### 2. 组件测试：交互与渲染验证

用 Testing Library 模拟用户点击、输入，验证组件行为，而不是去测实现细节。

### 3. 接口集成测试：Mock 掉不稳定依赖

后端没就绪时，用 MSW 拦截请求返回假数据，前端照样把链路跑通。

### 4. E2E：只覆盖核心主流程

E2E 维护成本高，我只挑「登录 → 核心操作 → 退出」这类最关键的冒烟路径，不追求全覆盖。

## 二、轻量化接入，别一上来就大动干戈

新人最容易犯的错是把测试体系搞得很重：一堆配置文件、覆盖率门槛卡死 CI，结果大家嫌烦干脆不写。

我的做法是：先能跑起来再说。本地 `vitest` 一键跑，CI 里加一条 `test` 命令，覆盖率先不卡。等业务稳定了再慢慢加门槛。

## 三、接上 CI，价值才真正释放

自动化测试最大的价值在 CI。每次 push 自动跑，红了就合不进去，从机制上拦住回归。

> 经验之谈：测试不是写给自己看的，是写给三个月后接手项目的同事看的。命名清楚、断言明确，比覆盖率数字重要得多。

## 小结

新项目早做自动化，核心是「分层 + 轻量 + CI」三件事。不要追求一步到位，先让第一条例子跑起来，剩下的会自然长出来。
