## 前言

做前端自动化也有挺长时间了，Selenium 是入门就接触的工具，网上教程最多，公司老项目也全用它写的。

之前一直觉得自动化测试就这样，偶尔报错、折腾环境都正常。直到去年接了个 Vue 后台项目，用 Selenium 写 E2E，天天被偶发失败搞心态，才下决心试 Playwright。

这大半年用下来，新项目我彻底不考虑 Selenium 了。聊聊真实感受，不搬官方参数。

## 一、光环境搭建，差距就很大

Selenium 要单独装对应浏览器的驱动：Chrome 下 chromedriver，火狐下 geckodriver，版本必须和本地浏览器完全对应，差一个小版本都可能跑不起来。

印象深的一次：周末 Chrome 偷偷更了新版，周一开脚本全红。翻半天找对应驱动，本地换完好了，推到 CI 又炸——服务器 Chrome 还是旧的。前前后后折腾快一小时。

团队人多了更麻烦，每人浏览器版本不同，还得反复说「先别更浏览器」，挺离谱的。

Playwright 完全没这问题，安装时自动下载适配好的浏览器，不用手动装驱动、配环境变量。

~~~bash
npm init playwright@latest
~~~

一行装完，本地、测试机、CI 全一致，不存在「我本地能跑你那跑不了」。

## 二、用例稳不稳定，最影响心态

自动化测试最磨人的不是写用例，是偶发失败。明明代码没改，今天过明天挂，排查半天找不到原因。

Selenium 的老毛病：现代页面全是异步渲染，接口没返回、DOM 没渲染，它就执行点击、取值，直接报找不到元素。你要么写死 sleep 等几秒，要么给每个元素写显式等待，代码又臭又长。

我之前写个表单提交用例，等弹窗、等下拉、等按钮可点，光等待就十几行，还偶尔抽风。

换 Playwright 后体验好太多：它自带自动等待，点击、填输入框会自己等元素加载好、可点了再操作，不用手动写等待。同样逻辑跑了几十次，一次没因元素没加载报过错。

> 现代前端页面全是动态渲染，Selenium 那套老思路跟不上了，Playwright 才是适配现在开发模式的。

## 三、其他让我留下的点

- 自带 trace viewer，失败能回放每一步，定位快十倍
- 网络拦截原生支持，Mock 接口比 Selenium 方便
- 多浏览器（Chromium / Firefox / WebKit）一套 API 搞定

## 小结

不是说 Selenium 不好，老项目维护它没问题。但新项目、尤其是动态渲染重的前端，Playwright 在环境、稳定性、调试上全方位省心。我现在的原则很简单：新项目无脑 Playwright。
